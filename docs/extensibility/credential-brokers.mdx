A credential broker is an operator-run gRPC service that decides the credential for each inspected HTTP request a sandbox sends to a selected host. The broker can place a credential on the request, send the request on without one, or deny it. The broker gets credentials from a source of its choice, such as a secret store or a token service.

## When to Use a Credential Broker

Use a credential broker when one central service must decide, on every request, which credential a sandbox gets for a resource. For example, a broker can:

- Grant access to a new upstream API without changing gateway or provider configuration.
- Revoke a sandbox's access to a host, effective on its next request.
- Rotate an upstream secret without restarting sandboxes.
- Exchange the agent's bearer token for a credential scoped to the target API.

A broker does not replace network policy. Policy admits the connection and the request before the broker runs. Use [provider token grants](/how-it-works/providers/profiles#dynamic-token-grants) instead when a credential belongs to one provider profile and its endpoints.

## How the Broker Fits the Request Path

The supervisor calls the broker at the credential injection step. The call comes after network policy, L7 policy, and [supervisor middleware](/extensibility/supervisor-middleware), and before provider token grants and placeholder resolution. It applies to inspected relays, TLS-terminated passthrough, and the forward proxy.

The broker answers with one decision:

| Decision | Result |
| --- | --- |
| `grant` | The supervisor writes the broker's credentials into the request. Provider token grants for those headers are skipped. Provider credentials for other headers still apply. |
| `pass` | The supervisor sends the request with provider credentials, as it does without a broker. |
| `deny` | The workload receives HTTP 403 with an `x-openshell-request-id` header. No provider credential is acquired. |

The supervisor does not cache decisions. Every request to a selected host gets a new call, so the broker can cache credentials but the supervisor never reuses an earlier decision.

The operator configures the broker in gateway TOML. Sandbox policy does not select it, and a sandbox user cannot detach it.

## Implement a Broker Service

A broker implements the `openshell.credential_broker.v1.CredentialBroker` gRPC service defined in [`proto/credential_broker.proto`](https://github.com/NVIDIA/OpenShell/blob/main/proto/credential_broker.proto):

- `Describe` returns the broker's name, expected audience, and protocol metadata. The gateway calls it at startup.
- `GrantHttpRequest` decides the credential for one request. Sandbox supervisors call it.

`Describe` must return extension metadata with protocol `1.0` and the capability `openshell.credential-broker.contract`. See [Protocol Negotiation](/extensibility/overview#protocol-negotiation).

### Request Fields

`HttpCredentialRequest` contains these fields:

| Field | Value |
| --- | --- |
| `request_id` | The ID the workload sees in `x-openshell-request-id` on a refusal. |
| `sandbox_id` | The calling sandbox, for audit. Authorize on the extension token instead. |
| `method` | The HTTP method. |
| `scheme` | `https`, or `http` for a plaintext request. |
| `host` | The destination host in lowercase, without brackets for IPv6. |
| `port` | The destination port. |
| `path` | The request path without the query string. |
| `authorization` | The workload's `Authorization` header values in wire order, before OpenShell resolves placeholders. Empty unless the registration sets `forward_authorization`. |

The request never includes the query string, the body, other headers, or a credential that OpenShell manages.

### Placements

A `grant` contains one to eight placements. A placement uses the same `auth_style`, `header_name`, and `query_param` fields as a [provider profile credential](/how-it-works/providers/profiles), plus the credential `value`. Provider token grants and the broker write placements with the same code.

| `auth_style` | What the supervisor writes |
| --- | --- |
| `bearer` | `Bearer <value>` in `header_name`, or in `Authorization` when `header_name` is empty. |
| `basic` | `Basic <base64(value)>` in `header_name`, or in `Authorization` when `header_name` is empty. The value is `user:password`. |
| `header` | The value in `header_name`, which is required. |
| `query` | The value in the query parameter `query_param`, which is required. |

Each placement replaces every instance of the header or query parameter it writes. Path placement is not supported, because request paths appear in access logs at every point that terminates TLS.

The supervisor rejects the whole grant, and fails the request with HTTP 502, when any placement breaks these rules:

- `auth_style` is not one of the four values above.
- A field that the style does not use is set, such as `query_param` with `bearer`.
- The value is longer than 8 KiB or contains a control character.
- The header is `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `Proxy-Connection`, `TE`, `Trailer`, `Upgrade`, an `x-openshell-*` header, or a header named in the request's `Connection` header.
- Two placements write the same header or query parameter.

A grant for a plaintext `http` request also fails with HTTP 502. OpenShell never sends a broker credential in cleartext. A `pass` or `deny` for a plaintext request is accepted.

### Denials

`CredentialDeny` has a reason. `DENY_REASON_ACCESS_DENIED`, or no reason, records the failure code `access_denied`. `DENY_REASON_AUTHORIZATION_REQUIRED` records `provider_authorization_required`. Both return HTTP 403 to the workload.

## Authenticate Supervisor Calls

Every `GrantHttpRequest` call has a short-lived extension token with `caller_kind` set to `supervisor` and the calling `sandbox_id`. The `Describe` call has a token with `caller_kind` set to `gateway`. Validate tokens as described in [Authenticating Extensions](/extensibility/overview#authenticating-extensions).

Authorize each request on the token's `sandbox_id` claim. The `sandbox_id` field in the request message is for audit only.

The supervisor fetches the broker's token at startup and rotates it with its middleware tokens. A call without an installed token fails with HTTP 502 and the failure code `unavailable`.

## Register a Broker

Start the broker before the gateway, then register it in gateway TOML:

```toml
[openshell.supervisor.credential_broker]
name = "corp-broker"
grpc_endpoint = "https://credential-broker.openshell.svc:8443"
tls_ca_cert_path = "/etc/openshell/certs/broker-ca.pem"
timeout = "1s"
include_hosts = ["**"]
exclude_hosts = ["status.example.com"]
forward_authorization = true
```

`openshell-gateway config preflight` validates the section. At startup the gateway also calls `Describe`, checks protocol metadata, and checks a non-empty `expected_audience` against the configured audience. The gateway does not start when the broker is unavailable or incompatible. An authenticated registration requires `[openshell.gateway.gateway_jwt]`.

The gateway sends the registration to every supervisor in the sandbox configuration. Restart the gateway after changing the section. See [Gateway Configuration](/how-it-works/gateways/configuration#credential-broker) for the field reference.

`include_hosts` and `exclude_hosts` use network policy host syntax. Exclusions take precedence. Select every host with `["**"]` when the broker answers `pass` for hosts it does not govern.

## Failures and Refusals

The broker fails closed. It has no `on_error` setting. The workload receives HTTP 502 with an `x-openshell-request-id` header when the broker call fails:

| gRPC status | Failure code |
| --- | --- |
| `UNAVAILABLE`, `RESOURCE_EXHAUSTED` | `unavailable` |
| `DEADLINE_EXCEEDED`, or the registration `timeout` expires | `timeout` |
| `UNAUTHENTICATED`, `PERMISSION_DENIED` | `workload_identity_rejected` |
| `INVALID_ARGUMENT`, `FAILED_PRECONDITION` | `configuration_error` |
| Any other status, a result without a decision, or an invalid grant | `unclassified` |

These failures use the stage `credential_broker`. OpenShell does not log the broker's status message. See [Token Grant Failures](/how-it-works/providers/profiles#token-grant-failures) for the recovery action of each code.

The supervisor refuses traffic to a selected host that it cannot parse as HTTP:

- A CONNECT tunnel to a `tls: skip` endpoint or non-HTTP traffic receives HTTP 403 with the error `credential_broker_required`.
- A transparent TCP connection is closed.

Each refusal emits a High OCSF detection finding. Exclude hosts that need `tls: skip` or raw TCP from `include_hosts`.

If a supervisor cannot install the registration it receives, it refuses every request with HTTP 502 and the code `configuration_error`, and refuses every uninspected connection, until it installs a valid one. It does not keep a previous registration, because a new one may select more hosts.

## Observe Broker Decisions

The supervisor records broker activity as OCSF events:

| Event | Severity | When |
| --- | --- | --- |
| `ConfigStateChange` | Informational | The supervisor installs or removes the registration. |
| `ConfigStateChange` | High | The supervisor rejects the registration. |
| `HttpActivity` | Informational | The broker grants or passes a request. |
| `HttpActivity` | Medium | The broker denies a request, or the call fails. The event includes the request ID. |
| `DetectionFinding` | High | The supervisor refuses uninspected traffic to a selected host. |

Events never include placement values, `Authorization` values, or broker error text. `openshell gateway info` lists the broker with the extension kind `credential-broker`.

## Current Limitations

- A gateway has one broker.
- The broker sees only the request target and, when enabled, `Authorization`. It cannot read other headers or the body, and it cannot replace the body.
- Registration changes require a gateway restart.
- [Extension authentication](/extensibility/overview#current-limitations) limits apply to broker tokens.
